这个项目（[2026graphrag](https://claude.ai/epitaxy/2026graphrag)）是一个基于 **Neo4j + neo4j_graphrag + DeepSeek(OpenAI兼容API)** 搭建的 GraphRAG 实验项目，包含知识图谱构建（extract）、检索问答（rag_vector/rag_graph）、Flask 后端 API（backend/api.py）和前端可视化（frontend + vis.js）。下面按你要的三个方面详细讲解。

## 一、实体/关系抽取（Entity & Relation Extraction）

核心逻辑在 [build_kg_simple.py](https://claude.ai/epitaxy/2026graphrag/graphragexpr/extract/build_kg_simple.py) 和 [build_kg_dyn.py](https://claude.ai/epitaxy/2026graphrag/graphragexpr/extract/build_kg_dyn.py)，抽取方式是**纯 LLM Prompt 抽取**，没有用 `SimpleKGPipeline` 这种官方组件，而是手写调用 DeepSeek Chat 模型：

1. **抽取方式**：把原文整段（或分块后的每个 chunk）塞进 prompt，要求模型直接输出 JSON：

   ```json
   {
     "entities": [{"name": "...", "type": "..."}],
     "relationships": [{"source": "...", "target": "...", "type": "..."}]
   }
   ```

   温度设为 0（保证确定性），并且 prompt 明确要求"自行决定本体类型和关系类型"——即**开放式本体（open schema）**，不预先定义实体/关系类型枚举，完全靠 LLM 自由生成类型标签（如"人物/地点/物品/概念"，在 [build_kg_dyn.py:74-78](https://claude.ai/epitaxy/2026graphrag/graphragexpr/extract/build_kg_dyn.py:74) 里对红楼梦场景给了 4 类提示，但仍不是硬性约束）。

2. **分块粒度**：

   - `build_kg_simple.py` 是单文本整体抽取（一个 doc = 一个 chunk）。
   - `build_kg_dyn.py`/`build_kg_simple_dynamic.py` 针对《红楼梦》长文本，先用 [sample_data_dyn.py](https://claude.ai/epitaxy/2026graphrag/graphragexpr/extract/sample_data_dyn.py) 按"第X回"章节标记切分，再按 `chunk_size=500` 字符切块（有 overlap），对每个 chunk 单独调用 LLM 抽取，最后把所有 chunk 的实体/关系合并（`all_entities.extend(...)`）。

3. **JSON 解析容错**：response 用 ````json` 代码块包裹时会做字符串切分提取，解析失败则返回空列表并打印报错，不会中断整个流程。

4. **实体去重与建图（写入 Neo4j）**：

   - 实体用 `MERGE (e:\`{entity_type}` {name: $name})`——动态标签（label 就是抽取出的实体类型字符串），按 `name` 属性去重合并，这意味着同名不同类型的实体会各自建一个节点（label 不同）。
   - 关系用 `MERGE (s)-[:\`{rel_type}`]->(t)`，关系类型同样是动态字符串（做了简单的空格转下划线清洗）。
   - 每个实体额外建一条 `FROM_CHUNK` 边连回它所在的文本块（`build_kg_dyn.py` 里是"实体名是否出现在chunk文本中"这种朴素字符串匹配来判定归属，而不是 LLM 精确溯源）。

   这种做法的特点：**没有实体消歧/规范化**（比如"贾宝玉"和"宝玉"会被当成两个不同节点），也没有 embedding 相似度合并，纯靠字符串完全匹配 MERGE。

## 二、检索方式（Retrieval）

项目基于 `neo4j_graphrag` 库的 Retriever 体系，提供了四种检索策略，在 [backend/api.py:266-346](https://claude.ai/epitaxy/2026graphrag/backend/api.py:266) 的 `/api/graphrag` 接口里可以按 `method` 参数切换：

| method          | 检索器                                                       | 原理                                                         |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `vector`        | `VectorRetriever`（见 [rag_vector.py](https://claude.ai/epitaxy/2026graphrag/graphragexpr/extract/rag_vector.py)） | 纯向量检索：query 文本 embedding 后在 Neo4j 向量索引 `text_embeddings`（建在 `Chunk.embedding` 上，见 [create_index.py](https://claude.ai/epitaxy/2026graphrag/graphragexpr/extract/create_index.py)）上做 cosine 相似度 top-k，只返回 chunk 文本 |
| `vector_cypher` | `VectorCypherRetriever`（见 [rag_graph.py](https://claude.ai/epitaxy/2026graphrag/graphragexpr/extract/rag_graph.py)） | 先向量检索命中 chunk，再执行一段自定义 Cypher：从 chunk 通过 `FROM_CHUNK` 反向找到关联实体，沿关系向外扩展 1~2 跳（`rel*1..2`），把扩展到的三元组和原始 chunk 文本一起拼成上下文——**这就是"图遍历增强检索"（graph traversal augmented retrieval）**的核心 |
| `hybrid`        | `HybridRetriever`                                            | 向量检索 + 全文检索（`text_fulltext` 索引）融合排序，返回 chunk 文本 |
| `hybrid_cypher` | `HybridCypherRetriever`                                      | hybrid 检索基础上叠加同样的图遍历 Cypher，语义+关键词+图结构三路融合 |

**自定义 Cypher 检索的关键设计**（[rag_graph.py:50-67](https://claude.ai/epitaxy/2026graphrag/graphragexpr/extract/rag_graph.py:50)）：

```cypher
WITH node AS chunk
MATCH (chunk)<-[:FROM_CHUNK]-(entity)-[rel*1..2]-(neighbor)
...
RETURN '=== 相关文本 ===\n' + joined_texts + '\n\n=== 相关知识 ===\n' + joined_triples AS info
```

用 `reduce()` 手写字符串拼接代替 APOC 插件的 `apoc.text.join`（说明部署环境没装 APOC，纯 Cypher 兼容性写法），把"命中的原文段落"和"图上扩展出的三元组"两类信息拼在一起，形成检索结果。

`backend/api.py` 还额外做了一步：对 `*_cypher` 方法，检索完成后**单独再查一次 Neo4j**，把用到的子图（节点+边）提取出来返回给前端做可视化（[api.py:373-451](https://claude.ai/epitaxy/2026graphrag/backend/api.py:373)），这样前端不仅能看到答案，还能看到"回答依据的是哪一小片图"。

## 三、知识注入形式（Knowledge Injection）

采用的是标准 **RAG（检索后拼 prompt）**方式，而非微调或结构化工具调用：

1. **Prompt 模板**（`RagTemplate`，见 [rag_graph.py:76-89](https://claude.ai/epitaxy/2026graphrag/graphragexpr/extract/rag_graph.py:76) 和 [backend/api.py:349-362](https://claude.ai/epitaxy/2026graphrag/backend/api.py:349)）：

   ```
   你是一个专业的问答助手。请仅根据以下上下文回答问题，
   上下文包括相关文本片段和知识图谱三元组。如果上下文不足以回答，请如实说明。
   
   # 问题：{query_text}
   # 上下文：{context}
   # 回答：
   ```

   要求模型"仅根据上下文回答"、"上下文不足要如实说明"——典型的**限定上下文 + 拒绝幻觉**指令，context 里混合了两种异构信息：

   - 非结构化文本（原始 chunk 内容）
   - 结构化知识（图遍历得到的三元组，格式化成 `实体A -[关系]-> 实体B` 这种可读字符串）

2. **注入粒度**：不是把整张图或整个 embedding 向量喂给 LLM，而是**先图查询、再序列化成自然语言字符串、再塞进 prompt**——这是 GraphRAG 的典型做法：图结构本身不直接进模型，是"结构→文本"的转译。

3. **向量维度对齐**：`ExternalEmbedder`（[external_embedder.py](https://claude.ai/epitaxy/2026graphrag/graphragexpr/external_embedder.py)）优先用外部 embedding API（`EMBED_ENDPOINT/EMBED_MODEL/EMBED_TOKEN` 配置），若未配置则 fallback 到一个 hash-based 的假 embedder（`custom_embedder.SimpleHashEmbedder`），保证没有真实 embedding 服务时也能跑通流程（demo 友好但检索质量会很差）。索引维度固定 1536（对齐 `text-embedding-3-small`），embedding 维度不匹配时会做 pad/truncate 兜底。

**整体链路总结**：LLM 开放式抽取（无预定义 schema）→ 字符串精确匹配去重后 MERGE 进 Neo4j（动态 label/关系类型）→ 向量索引 + 图遍历双通道检索 → 检索结果序列化为"文本+三元组"混合上下文 → 限定上下文的 prompt 模板注入 LLM 生成答案。整个系统更偏"教学/实验性质"的最小可行 GraphRAG 实现，重点在打通全链路而非工程健壮性（比如没有实体消歧、chunk-实体关联靠字符串包含判断等）。
