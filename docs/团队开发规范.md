# 《中药学》GraphRAG 多人协作开发 Skill

## 1. 目标

所有参与者与编码代理必须共同遵守本 Skill，确保项目能够：

1. 从教材原文稳定构建可审计知识图谱；
2. 通过类型化检索与关键路径检索获得低噪声证据；
3. 按问题类型将证据组织为卡片、表格、矩阵、路径或摘要；
4. 对每个关键结论提供可验证的 Chunk、页码和逐字证据；
5. 支持多人并行开发、消融实验、版本回滚和 Linux 部署。

本 Skill 的优先级高于个人编码习惯。若任务要求与本 Skill 冲突，先指出冲突，不得静默绕过。

## 3. 不可违反的架构原则

### 3.1 证据优先

- 每个 `ACCEPTED` Assertion 必须有 `chunk_id`、页码和可定位 `evidence_quote`。
- 禁止将 LLM 常识、模型补全或链路预测直接写入正式事实图。
- 证据无法定位时只能 `REVIEW` 或 `REJECTED`。
- 高风险字段包括剂量、毒性、禁忌、孕妇、儿童、不良反应和配伍禁忌；证据不足必须拒答。

### 3.2 双层图

- `Assertion/Evidence Graph` 是事实源。
- 类型化实体间关系是可重建的 `Serving Projection`。
- 检索可以读取 Serving Edge，但审计、版本、多来源和冲突必须回到 Assertion。
- 不允许只保存直接边而丢失证据与版本。

### 3.3 稳定身份

- 实体身份使用 `canonical_id`，禁止使用 `name` 作为唯一身份。
- Chunk、Assertion、Run、Document 必须使用稳定 ID。
- 展示名、别名、OCR 表面形式不能替代稳定 ID。
- 不允许对实体 `name` 建全局唯一约束。

### 3.4 受控本体

- 实体类型与关系 ID 只从 `domain/ontology.yaml` 和 `domain/ontology.py` 读取。
- 禁止 LLM 自由创建正式标签或关系类型。
- 每个关系必须定义 domain/range、中文展示名、是否高风险和允许的限定符。
- 未知类型或非法起止类型必须记录并拒绝，不能统一降级为“概念”。

### 3.5 检索按意图规划

支持的主要意图：

```text
attr
reverse
intersect
compare
path
fallback
```

- 简单属性问题不得强制走 PathRAG。
- 多跳路径只允许领域关系白名单，默认最大 3 跳。
- 图扩展不得穿过 `Chunk/Document/Mention/Assertion` 审计边形成伪路径。
- PPR、图距离或链路预测只能排序候选，不能创造教材事实。

### 3.6 结构化注入

检索层输出 `EvidencePacket`，生成层不得直接查询 Neo4j。

结构映射：

```text
attr       -> card/table
reverse    -> ranked table
intersect  -> constraint matrix
compare    -> aligned comparison table + evidence
path       -> ordered path bundle
safety     -> quote-first evidence cards
fallback   -> ranked source chunks
```

只有完整实现原论文算法时，文档中才可写“复现 PathRAG/StructRAG”；否则统一写“PathRAG-inspired”或“StructRAG-inspired”。

### 3.7 版本化与原子发布

- 新构建写入 `IngestRun(status=BUILDING)`。
- 质量检查通过后原子切换为 `ACTIVE`。
- 失败构建标记 `FAILED`，旧 `ACTIVE` 版本继续服务。
- 禁止默认 `DETACH DELETE` 全库。
- Prompt、Schema、模型、OCR 参数、Embedding 改动必须升版本并进入缓存键。

### 3.8 技术边界

- Neo4j 固定为团队冻结的版本，默认基线为 5.26 LTS。
- 使用原生 `neo4j` Python Driver；主链不得依赖 `neo4j-graphrag`。
- 目标运行平台为 Linux。
- `hash embedding` 只允许单元测试，禁止用于正式评测和演示结论。
- 密钥只从环境变量或密钥管理系统读取，禁止提交 `.env` 和 token。

## 5. 模块边界与所有权

```text
config/domain
  ↑
ingest
  ↑
extract/linking
  ↑
storage
  ↑
retrieval
  ↑
structuring
  ↑
generation
  ↑
api/frontend
```

`evaluation` 可读取各层公开接口，但不得复制业务逻辑。

### 5.1 `config/`

负责：

- 环境变量；
- Feature Flag；
- 阈值；
- 模型与索引版本；
- 超时与重试；
- token 和候选数量预算。

规则：

- 不得在业务文件散落魔法常量。
- 所有默认值有注释与配置来源。
- 评测运行必须保存完整配置快照。

### 5.2 `domain/`

唯一事实源：

- Pydantic/dataclass 模型；
- 本体与关系白名单；
- 枚举；
- 领域异常；
- ID 与哈希函数。

任何公共字段变更都属于契约变更。

### 5.3 `ingest/`

只负责：

- OCR；
- bbox/置信度；
- 页面质量；
- 章节与药物条目结构；
- 抽取单元与 parent-child Chunk。

不得调用 Neo4j 检索或生成答案。

### 5.4 `extract/` 与 `linking/`

负责：

- 严格结构化初始抽取；
- 实体候选生成；
- 实体消歧；
- 关系规则验证；
- 模糊项 LLM 复核；
- 跨 Chunk 候选补全。

不得直接决定发布哪个 Run；只输出结构化候选与验证结果。

### 5.5 `storage/`

负责：

- Neo4j 连接生命周期；
- 索引和约束；
- 批量写入；
- Assertion 事实源；
- Serving Projection；
- Run 激活/回滚；
- 数据迁移。

所有写操作必须幂等或有明确事务边界。

### 5.6 `retrieval/`

负责：

- 查询实体链接；
- 路由；
- sparse/dense/entity recall；
- RRF 与重排；
- 定向遍历；
- 交集；
- 关键路径；
- trace。

输出只能是结构化候选或 `EvidencePacket`，不得生成最终自然语言答案。

### 5.7 `structuring/`

负责把 `EvidencePacket` 转换为确定性结构：

- 卡片；
- 表格；
- 约束矩阵；
- 路径包；
- 章节摘要包；
- 高风险证据卡。

序列化结果必须保留 `evidence_id` 和页码。

### 5.8 `generation/`

负责：

- Prompt 构造；
- LLM 调用；
- Claim 抽取；
- 引用验证；
- 拒答；
- 安全提示。

不得把未进入本次 `EvidencePacket` 的知识写进答案。

### 5.9 `api/` 与 `frontend/`

- API 只编排服务，不复制检索逻辑。
- 保持 `answer/method/subgraph/sources` 兼容。
- 新增字段只增不删，破坏性变更必须升 API 版本。
- 子图必须与实际上下文同源，不允许为了可视化再次执行不同查询。

## 7. ID、证据与评分规范

### 7.1 ID

- `document_id`：文件哈希 + 版本/版次；
- `chunk_id`：文档、结构路径与规范化内容哈希；
- `canonical_id`：稳定领域 ID，不随展示名变化；
- `fact_key`：主语、谓词、宾语/值、限定符与极性的哈希；
- `assertion_id`：事实键 + 来源 Chunk + 证据跨度 + Schema 版本；
- `run_id`：UUIDv7/ULID。

禁止使用数组顺序、数据库内部 `elementId` 或自增序号作为跨版本外部 ID。

### 7.2 证据

- 优先保存原文字符跨度。
- 规范化匹配不得覆盖原始证据。
- 模糊匹配必须记录 `match_mode` 和距离。
- 无法定位的证据不能 `ACCEPTED`。
- 跨 Chunk 事实保存全部来源 Chunk，同时标记主语来源和宾语/属性来源。

### 7.3 评分

所有分数都必须注明语义：

```text
retrieval_score  查询相关性
rule_score       确定性规则支持度
final_score      规则与复核后的决策支持值
path_score       路径排序分
```

禁止把任何分数描述为“事实正确概率”，除非经过单独的概率校准实验。

## 8. LLM 调用规范

统一通过 `LLMClient`：

- 超时；
- 指数退避；
- 最大重试；
- 限流；
- JSON Schema/Pydantic 校验；
- token 与成本统计；
- request_id；
- 模型、Prompt、Schema 版本；
- 失败清单；
- 可替换供应商。

规则：

1. 业务模块不得自行拼 HTTP 请求。
2. Prompt 输出必须是严格 JSON，禁止从自然语言中正则猜字段作为正式结果。
3. LLM confidence 只能作候选信号。
4. 二次校验只依据提供证据，不允许调用常识。
5. 重试不得改变事实语义；非法输出超过上限后进入失败队列。
6. 测试中使用 FakeLLM/录制响应，不依赖在线 API。

## 9. Neo4j 与 Cypher 规范

### 9.1 连接

- 进程生命周期内复用一个 Driver；
- 每次事务显式指定 database；
- 读写使用托管事务或 `execute_query`；
- 关闭 session/driver；
- 不在模块导入时建立网络连接。

### 9.2 写入

- 批量使用 `UNWIND`；
- 每批大小配置化；
- 关系类型只能来自白名单；
- 禁止把用户输入、模型输出直接拼成 Cypher；
- 动态关系类型若必须拼接，先映射为受控常量并按类型分组；
- 写入失败必须回滚或标记 Run 失败。

### 9.3 约束与索引

必须至少包含：

```text
Entity.canonical_id UNIQUE
Chunk.chunk_id UNIQUE
Assertion.assertion_id UNIQUE
Document.document_id UNIQUE
IngestRun.run_id UNIQUE
```

名称只建普通索引/全文索引，不建身份唯一约束。

向量索引维度必须与运行时模型维度一致；不一致直接 health 失败，不得静默降级。

### 9.4 图遍历

- 只走领域关系白名单；
- 审计边不参与推理路径；
- 路径长度、节点数、分支数配置化；
- 查询必须有超时；
- 返回结果必须带 `fact_key/evidence_ids`。

## 10. 检索规范

### 10.1 召回

默认三路：

```text
全文召回
向量召回
实体/别名召回
```

- 各路独立排序；
- 使用 RRF 或明确的 rank fusion；
- 不直接比较全文原始分与向量原始分；
- 自研 BM25 只在候选集上精排；
- 所有 k 值由配置与评测冻结。

### 10.2 实体链接

顺序：

```text
规范名/别名精确匹配
→ 最长匹配
→ 字符候选
→ 向量候选
→ 类型/上下文重排
→ 模糊项复核
```

向量阈值只能召回候选，不能直接确认同一实体。

缓存键使用 `active_run_id + graph_revision + schema_version`，不得使用节点数量。

### 10.3 路由

规则优先，LLM 兜底。比较词、否定词和高风险词的规则优先级必须在实体数量规则之前。

路由输出必须包含原因和置信信息，写入 trace。

### 10.4 交集

- 先硬交集；
- 再约束覆盖率；
- 若使用 PPR，对每个种子分别计算并聚合；
- 明确标记 `exact_match` 与 `partial_match`；
- 软排序结果不能表述为“教材明确同时满足”。

### 10.5 路径

- 默认最大 3 跳；
- 只处理必要的多跳意图；
- 每条边有证据；
- 路径去重；
- 优先高支持、短路径；
- 结果写入 `EvidencePacket.path`；
- 不把整个邻域附加给模型。

## 11. 结构化注入与生成规范

### 11.1 确定性序列化

表格、矩阵和路径由程序生成，不让 LLM决定列名、页码或 evidence_id。

每项至少显示：

```text
事实/路径
证据原句
页码
支持度
是否跨块
```

### 11.2 Prompt 分区

推荐固定顺序：

```text
[任务与回答边界]
[问题]
[结构化证据]
[教材原文]
[引用规则]
[输出 JSON Schema]
```

高风险问题增加：

```text
禁止提供教材证据之外的剂量、禁忌或临床建议。
证据不足时必须 abstain。
```

### 11.3 Claim–Evidence 校验

- 每个关键 Claim 至少关联一个 `evidence_id`；
- `evidence_id` 必须属于本次 EvidencePacket；
- 数字、单位、否定、对象必须与证据一致；
- 无支持句删除、重写或拒答；
- 引用页码由程序填充，不由模型自由生成。

## 12. 代码规范

默认：

```text
Python >= 3.11
UTF-8
4 空格
行宽 100
完整类型标注
Pydantic v2 / dataclass
pytest
ruff
mypy 或 pyright
```

### 12.1 命名

- 代码标识符使用英文；
- 领域稳定 ID 使用英文大写枚举；
- 中文只用于展示名、Prompt、文档和必要注释；
- 布尔变量使用 `is_/has_/use_/should_`；
- 不使用含义不明的 `data/info/result2/tmp`。

### 12.2 函数

- 单一职责；
- 显式输入输出；
- 避免隐藏全局状态；
- 不在函数内部读取散落环境变量，统一注入 Settings；
- 公共函数有 docstring，说明异常与副作用；
- 复杂算法给出公式、边界和复杂度说明。

### 12.3 错误与日志

- 使用项目异常类型；
- 禁止空 `except`；
- 禁止静默吞掉失败；
- 日志结构化，至少含 `request_id/run_id/chunk_id/module/status`；
- 不记录密钥、完整 token 或隐私数据；
- 库代码禁止 `print`。

### 12.4 配置

- 所有阈值、k、预算、开关进入 `Settings`；
- `.env.example` 不含真实密钥；
- 评测保存配置快照；
- 环境差异不得通过硬编码 Windows/Linux 路径处理。

## 13. Git 与 PR 规范

### 13.1 分支

```text
feat/<module>-<short-name>
fix/<module>-<short-name>
refactor/<module>-<short-name>
eval/<experiment-name>
docs/<topic>
```

禁止所有人长期直接在同一分支开发。

### 13.2 Commit

建议 Conventional Commits：

```text
feat(retrieval): add typed attr traversal
fix(linking): prevent same-name false merge
test(extract): add cross-chunk gold cases
docs(adr): choose assertion serving projection
```

一个 Commit 尽量对应一个逻辑变化。

### 13.3 PR 必填内容

```markdown
## 目的
## 设计与取舍
## 修改文件
## 数据/Schema/API 是否变化
## 测试
## 指标影响
## 风险与回滚
## 截图或示例（如适用）
```

### 13.4 合并门槛

- lint、typecheck、unit test 全通过；
- 契约测试通过；
- 公共接口有至少一名相邻模块成员 Review；
- Schema/Prompt/索引变化有版本号；
- 无密钥、缓存、大模型权重和大体积临时数据；
- 无虚构指标；
- 相关文档同步更新。

---

## 14. 测试规范

### 14.1 单元测试

每个模块覆盖：

- 正常路径；
- 空输入；
- 非法 Schema；
- 超时/重试；
- OCR 噪声；
- 否定与数值；
- 重复与幂等；
- 降级路径。

### 14.2 契约测试

必须覆盖：

```text
ChunkRecord
EntityRecord
AssertionRecord
EvidencePacket
QAResponse
LLM JSON Schema
Neo4j index/constraint
Frontend response keys
```

### 14.3 集成测试

至少：

1. 两个 Chunk 共同构成一条事实；
2. 同名不同类型实体不得错误连边；
3. Prompt/Schema 版本变化后缓存失效；
4. 新 Run 失败时旧 ACTIVE 仍可查询；
5. attr 跨页聚合；
6. reverse 查药；
7. intersect 硬交集与部分满足；
8. path 过滤审计边；
9. 无 provenance 的剂量问题拒答；
10. subgraph 与实际 evidence 同源。

### 14.4 金标准与评测

- 开发集和测试集分离；
- 测试集不得根据当前输出反向修改；
- 关键样本双人标注；
- 所有实验记录 git commit、run_id、模型、Prompt、Schema、Embedding 和配置；
- 报告均值之外还要报告分题型结果与失败案例；
- 小样本不得声称统计显著，除非实际完成相应检验。

## 15. 变更管理

以下变化必须创建 ADR：

- 本体实体类型或关系；
- Assertion 与 Serving Projection 模型；
- 公共字段删除/改名；
- Neo4j 版本升级；
- Embedding 模型/维度变化；
- Query intent 增删；
- Prompt 输出 Schema 改动；
- PathRAG/StructRAG 落地范围变化；
- 发布与回滚机制变化。

ADR 模板：

```markdown
# ADR-XXXX 标题
- 状态：Proposed / Accepted / Superseded
- 背景
- 决策
- 备选方案
- 影响
- 迁移方案
- 回滚方案
```

## 16. Definition of Done

任务只有同时满足以下条件才算完成：

- [ ] 功能符合验收条件；
- [ ] 公共契约未被私自破坏；
- [ ] 有单元/契约/必要集成测试；
- [ ] lint 和类型检查通过；
- [ ] 日志、异常、超时和降级完整；
- [ ] 新字段有类型、文档和迁移；
- [ ] Prompt/Schema/模型变化已升版本；
- [ ] 缓存键正确；
- [ ] 指标在冻结评测集上运行；
- [ ] 没有无证据正式事实；
- [ ] 没有 `name` 唯一身份；
- [ ] 没有 hash embedding 污染正式结果；
- [ ] 没有密钥、绝对本机路径或临时文件；
- [ ] PR 说明风险和回滚；
- [ ] 相关架构/使用文档同步更新。

## 17. 编码代理的输出格式

编码代理完成任务后必须按以下格式汇报：

```markdown
## 完成内容
## 修改文件
## 关键设计决定
## 测试与结果
## 未解决问题
## 风险与回滚
## 下一依赖
```

禁止：

- 声称未运行的测试“已通过”；
- 填写虚构评测分数；
- 未经要求大范围重构；
- 用 TODO 代替核心功能后宣称完成；
- 隐藏失败记录；
- 将推测写成仓库事实；
- 因为方便而绕过 Schema、证据或版本机制。

## 18. 团队协作角色建议


## 19. 常用验收命令约定

仓库应逐步提供统一入口；名称可按项目实际调整，但团队不得各自保留一套脚本：

```bash
make setup
make lint
make typecheck
make test
make test-integration
make health
make eval-extraction
make eval-retrieval
make eval-generation
make run-api
```

在这些命令尚未建立前，PR 中必须列出等价的完整命令，不得只写“本地测试通过”。

## 20. 最终质量准则

所有设计与代码变更都用四个问题检查：

1. **事实能否回到教材原句？**
2. **实体和关系是否使用稳定、受控的身份？**
3. **检索是否只取回答该问题所需的证据？**
4. **该变化是否能被测试、消融、回滚和复现？**

任一问题答案为“不能”，该实现不得进入主分支。
